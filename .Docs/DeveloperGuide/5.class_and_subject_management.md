# DEV-05 — Class & Subject Management
**EduTool Developer Guide**
> Covers: Subject setup, class setup, auto-enrollment engine, week/session computation, class archiving.

---

## 1. Overview

Subjects define what is taught and when. Classes are the live instances of subjects — they have students, an educator, a rubric, and all the lesson/assessment/attendance content. Admin creates both. Educators manage content inside classes.

This guide covers the Admin-side structure. Content inside classes (lessons, assessments, grades, attendance) is covered in DEV-06 through DEV-09.

## 2. Subject Management

### 2.1 Data Model

```
Subject
  id              UUID, primary key
  org_id          FK → Organization
  title           string, e.g. "Data Structures", "Biology 101"
  level_section   enum (ELEMENTARY | HIGH_SCHOOL | SENIOR_HIGH | COLLEGE)
  grade_year      string, e.g. "Grade 3", "Year 2"
  strand_id       FK → Strand, nullable (Senior High only)
  course_id       FK → Course, nullable (College only)
  educator_id     FK → Educator
  weekdays        array of enum (MON | TUE | WED | THU | FRI), min 1, max 5
  time_start      time
  time_end        time
  is_locked       boolean, default false
  school_year_id  FK → SchoolYear
  created_at      timestamp
```

### 2.2 Lock/Unlock Cycle

| State | Condition | Behavior |
|---|---|---|
| Unlocked | Start of school year | Admin can edit all fields freely |
| Locked | Admin manually locks | All fields become read-only |
| Auto-unlocked | New school year activated | All subjects for previous year remain locked; new-year subjects start unlocked |

Only Admin can lock subjects. Locking is a manual action — there is no auto-lock for subjects (unlike grade locks which have a deadline auto-lock).

Once locked, subjects cannot be unlocked by any role within that school year.

### 2.3 Schedule Conflict Validation

Run this validation when Admin creates or edits a subject (before saving):

**Type 1 — Same level, same time slot, same day:**
```
FOR each new weekday + time_start + time_end in the subject being saved:
  existing = find subjects where:
    org_id = this org
    school_year_id = this school year
    level_section = this level_section
    grade_year = this grade_year
    strand_id = this strand_id (if applicable)
    course_id = this course_id (if applicable)
    id != this subject (exclude self)
    weekdays contains this weekday
    time ranges overlap:
      NOT (time_end <= existing.time_start OR time_start >= existing.time_end)
  IF existing found:
    ERROR: "Schedule conflict: [existing subject title] is already scheduled
            at this time on [weekday] for [grade_year]."
```

**Type 2 — Educator double-booking:**
```
FOR each new weekday + time range:
  existing = find subjects where:
    org_id = this org
    school_year_id = this school year
    educator_id = this educator_id
    id != this subject
    weekdays contains this weekday
    time ranges overlap
  IF existing found:
    ERROR: "Educator [Name] is already assigned to [subject title]
            at this time on [weekday]."
```

Both validations check across ALL year levels within the same course/strand — not just the same grade year.

## 3. Class Management

### 3.1 Data Model

```
Class
  id                UUID, primary key
  org_id            FK → Organization
  school_year_id    FK → SchoolYear
  title             string
  subject_id        FK → Subject, nullable (class can exist independently)
  level_section     enum
  grade_year        string
  strand_id         FK → Strand, nullable
  course_id         FK → Course, nullable
  section_id        FK → Section, nullable (if targeting a specific section)
  semester_id       FK → SemesterPeriod
  educator_id       FK → Educator
  weekdays          array of enum (MON | TUE | WED | THU | FRI)
  time_start        time
  time_end          time
  capacity          integer, nullable (null = unlimited)
  is_archived       boolean, default false
  archived_at       timestamp, nullable
  deleted_at        timestamp, nullable (soft delete)
  created_at        timestamp
```

### 3.2 Class Creation Rules

- `weekdays`: 1 to 5 days. Each day is a session day.
- `section_id`: optional. If set, auto-enrollment only matches students in that section.
- `capacity`: optional. If set, enrollment is capped at this number.
- On creation, the system immediately runs auto-enrollment for all matching Active students (see Section 4).

### 3.3 Rubric Assignment on Creation

When a class is created, Admin (or the Educator) assigns a rubric:
- (a) Use the org's Admin default rubric
- (b) Pick from the assigned educator's personal rubric library
- (c) Build from scratch

Rubric **locks permanently** once the first student is enrolled in the class. See DEV-09 for rubric model and rules.

## 4. Auto-Enrollment Engine

This is a core service used by multiple flows: student account save, student profile update, class creation, Admin manual enrollment.

### 4.1 Trigger Points

| Trigger | Direction |
|---|---|
| Student account created / profile saved | Find matching classes → enroll student |
| New class created | Find matching students → enroll them |
| Admin manually adds subject to student | Single enrollment with capacity check |

### 4.2 Matching Logic

A student matches a class if ALL conditions are true:

```
student.level_section = class.level_section
AND student.grade_year = class.grade_year
AND (class.strand_id IS NULL OR class.strand_id = student.strand_id)
AND (class.course_id IS NULL OR class.course_id = student.course_id)
AND (class.section_id IS NULL OR class.section_id = student.section_id)
AND class.school_year_id = currentActiveSchoolYear.id
AND class.is_archived = false
AND student.status = 'ACTIVE'
```

### 4.3 Enrollment Model

```
Enrollment
  id              UUID, primary key
  student_id      FK → Student
  class_id        FK → Class
  enrolled_at     timestamp
  added_by        enum (AUTO | ADMIN)
  manual          boolean  -- true if Admin forced outside profile match
  deleted_at      timestamp, nullable (soft delete = unenrolled)
```

### 4.4 Enrollment Loop

```
FUNCTION enrollMatchingStudents(class_id):
  class = getClass(class_id)
  students = getActiveStudentsMatchingClass(class)

  FOR each student in students:
    -- Duplicate check
    existing = getEnrollment(student.id, class.id)
    IF existing AND existing.deleted_at IS NULL:
      CONTINUE  -- already enrolled

    -- Capacity check
    IF class.capacity IS NOT NULL:
      count = countActiveEnrollments(class.id)
      IF count >= class.capacity:
        CREATE PendingEnrollment { student_id, class_id, reason: CLASS_CAPACITY }
        NOTIFY Admin: "Student [Name] could not be enrolled in [Class Title]:
                        class is full."
        CONTINUE

    -- Enroll
    CREATE Enrollment { student_id, class_id, added_by: AUTO }
    NOTIFY educator: "New student [Name] has been added to your class [Title]."
    LOG: action = AUTO_ENROLLED

FUNCTION enrollMatchingClasses(student_id):
  student = getStudent(student_id)
  classes = getMatchingClasses(student)
  -- Same logic as above but iterating over classes for a single student
```

## 5. Session & Week Computation

Sessions are the individual meeting instances of a class. They are generated for the full semester duration when a class is created (or when the semester starts, depending on your implementation preference).

### 5.1 Session Model

```
ClassSession
  id              UUID, primary key
  class_id        FK → Class
  date            date
  weekday         enum (MON | TUE | WED | THU | FRI)
  week_number     integer  -- e.g. 1, 2, 3
  week_sub_index  integer, nullable  -- e.g. 1, 2, 3 within a week
  week_label      string  -- computed, e.g. "Week 1", "Week 1.2"
  is_skipped      boolean, default false  -- set if falls on calendar event
  created_at      timestamp
```

### 5.2 Week Label Rules

| Class weekday count | Week label format |
|---|---|
| 1 weekday | "Week 1", "Week 2", "Week 3" ... |
| 2 weekdays | "Week 1.1", "Week 1.2", "Week 2.1", "Week 2.2" ... |
| 3 weekdays | "Week 1.1", "Week 1.2", "Week 1.3", "Week 2.1" ... |
| 4 weekdays | "Week 1.1" through "Week 1.4" ... |
| 5 weekdays | "Week 1.1" through "Week 1.5" ... |

### 5.3 Session Generation Algorithm

```
FUNCTION generateSessions(class_id):
  class = getClass(class_id)
  semester = getSemesterPeriod(class.semester_id)
  calendar_events = getCalendarEvents(class.org_id, class.school_year_id,
                      types: [HOLIDAY, NO_CLASS_DAY])

  sorted_weekdays = sort(class.weekdays, order: MON < TUE < WED < THU < FRI)
  week_number = 1
  current_date = semester.start_date

  WHILE current_date <= semester.end_date:
    -- Find which of the class's weekdays fall in this calendar week
    week_sessions = []
    FOR each weekday in sorted_weekdays:
      session_date = getDateOfWeekday(weekday, current_date)
                     -- find the date of this weekday in the current ISO week
      IF session_date < semester.start_date OR session_date > semester.end_date:
        CONTINUE  -- outside semester bounds

      is_blocked = calendarEventCovers(calendar_events, session_date)

      IF NOT is_blocked:
        week_sessions.append({ date: session_date, weekday: weekday })

    -- Assign labels
    IF week_sessions.length = 0:
      -- All days in this week were blocked, advance to next week
      -- Do NOT increment week_number (no label consumed)
    ELSE:
      IF sorted_weekdays.length = 1:
        -- Single-day class: no sub-index
        session.week_label = "Week {week_number}"
        week_number += 1
      ELSE:
        FOR i, session in enumerate(week_sessions):
          session.week_label = "Week {week_number}.{i+1}"
        week_number += 1

      CREATE ClassSession records for all sessions in week_sessions

    current_date = next Monday after current_date (advance by 1 ISO week)
```

### 5.4 Important Rules

- Sessions that fall on a `HOLIDAY` or `NO_CLASS_DAY` calendar event are skipped — no session record created, no week index consumed.
- If a calendar event is added retroactively after sessions were generated, do NOT auto-delete existing session records. Admin reviews manually.
- `week_label` is a computed/stored string for display. Always derive it from `week_number` + `week_sub_index` — do not trust the stored string for logic.

## 6. Class Archiving

### 6.1 Flow

At end of semester, Admin manually archives a class:

```
Step 1  Admin selects "Archive Class" from the class management view.
Step 2  System checks:
          IF class.is_archived = true: reject, already archived.
          Warn if any grades are not yet locked:
            "This class has [N] students with unlocked grades. Archiving will
             lock all grades. Confirm?"
Step 3  Admin confirms.
Step 4  Lock any remaining unlocked grades (triggers auto-publish of scores).
Step 5  Set class.is_archived = true, class.archived_at = now()
        Soft-delete: class.deleted_at = now()
        (The class is invisible in active views but fully preserved in DB.)
Step 6  Log in Admin Audit Log:
          action_type = "CLASS_ARCHIVED"
          details = { class_id, admin_id }
```

### 6.2 After Archiving

- Class is read-only for all roles.
- Students can still view their grades and transcript entries from this class.
- Educator can still view (read-only) lessons, assessments, and grades.
- Nothing is deleted.
