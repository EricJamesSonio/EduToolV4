## ADD TO: DEV-11 — Notifications, Audit Logs & Soft Delete

### Cross-Module Calls

**DEV-11 is called by everyone — it calls no one.**

DEV-11 is the only module with zero outbound dependencies. Every other module writes to it. It never reads from or calls other modules.

Build DEV-11 first. The three helpers must be globally injectable before anything else is built:

```
NotificationService.notify(recipientUserId, type, message, entityType?, entityId?)
AuditLogService.log(orgId, actorId, actionType, targetType, targetId, details)
ActivityLogService.log(educatorId, classId, eventType, details)
```

**Notification scheduled jobs read from other modules:**

```
ASSESSMENT_RELEASED job:
  → queries Assessment WHERE release_date <= now() AND status != RELEASED
    (DEV-07's Assessment table)
  → for each: notifies assigned students + updates assessment status

ASSESSMENT_DEADLINE_APPROACHING job:
  → queries Assessment WHERE end_date between (now + N hours)
    (DEV-07's Assessment table)
  → for each: notifies assigned students

MEETING_REMINDER job:
  → queries Meeting WHERE scheduled_at between (now + 15min)
    (DEV-10's Meeting table)
  → checks AcademicCalendarEvent (DEV-01) — skip if holiday
  → notifies invited students

GRADE_AUTOLOCK job:
  → queries GradeLockWindow WHERE deadline <= now (DEV-09's table)
  → calls DEV-09 GradeService.lockGrades() for each unlocked class

ASSESSMENT_AUTOCLOSE job:
  → queries Assessment WHERE end_date <= now AND status = RELEASED (DEV-07)
  → closes active attempts, marks drafts as NULL

NOTIFICATION_RETENTION job:
  → self-contained — only touches Notification table (own table)
```

These jobs live in the `jobs/` folder (DEV-00B structure), not inside DEV-11 itself. But they import from DEV-11's notification service and from the relevant module services.

# DEV-11 — Notifications, Audit Logs & Soft Delete
**EduTool Developer Guide**
> Covers: In-app notification system, notification retention, Admin audit log, Educator activity log, soft delete policy.

---

## 1. Overview

This guide covers the three cross-cutting systems that run underneath everything else: notifications (how users are informed of events), audit logs (how Admin and educators track what happened), and soft delete (how records are preserved without being destroyed).

Build these early. Nearly every other module writes to them.

---

## 2. Notification System

### 2.1 Data Model

```
Notification
  id              UUID, primary key
  org_id          FK → Organization
  recipient_id    FK → User
  type            enum (see Section 2.3)
  title           string
  message         text
  related_entity_type  string, nullable  -- e.g. "Class", "Assessment", "Meeting"
  related_entity_id    UUID, nullable
  created_at      timestamp
  archived_at     timestamp, nullable  -- set when older than 90 days
```

### 2.2 Rules

- **In-app only.** No email. No SMS.
- **No read/unread tracking.** Simple chronological list per user.
- Notifications are scoped to the recipient's org. Users never see notifications from other orgs.
- Notifications are fetched by recipient: `GET /notifications?recipient_id={user_id}`

### 2.3 Notification Types & Triggers

| Type | Recipient | Trigger |
|---|---|---|
| `CONCEPT_EXTRACTION_COMPLETE` | Educator | Background job finishes extraction |
| `ASSESSMENT_GENERATION_COMPLETE` | Educator | Background job finishes assessment generation |
| `ASSESSMENT_RELEASED` | Assigned students | `release_date` reached (scheduled job) |
| `ASSESSMENT_DEADLINE_APPROACHING` | Assigned students | N hours before `end_date` (scheduled job, e.g. 24h) |
| `SCORE_PUBLISHED` | Student | Educator publishes score (individual or batch) |
| `GRADES_LOCKED` | Students in class | Grade lock applied (manual or auto) |
| `CLASS_REASSIGNED` | New educator | Admin reassigns class to new educator |
| `MEETING_CREATED` | Invited students | On meeting creation |
| `MEETING_REMINDER` | Invited students | N minutes before `scheduled_at` (if not a calendar event day) |
| `GRADE_LOCK_WINDOW_OPENED` | All educators in org | Admin opens lock window |
| `AUTO_LOCK_APPLIED` | Affected educator | System auto-locks class at deadline |
| `AUTO_ENROLLED` | Student | Auto-enrollment triggered for student |
| `STUDENT_ADDED_TO_CLASS` | Educator | Admin manually adds student to class |
| `STUDENT_REMOVED_FROM_CLASS` | Educator | Admin removes student from class |
| `ENROLLMENT_PENDING_CAPACITY` | Admin | Capacity block prevents enrollment |

### 2.4 Notification Write Helper

All modules call this shared function:

```
FUNCTION notify(recipient_id, type, message, related_entity_type?, related_entity_id?):
  CREATE Notification {
    org_id: getUserOrg(recipient_id),
    recipient_id,
    type,
    title: NOTIFICATION_TITLES[type],  -- map type → short title string
    message,
    related_entity_type,
    related_entity_id,
    created_at: now()
  }
```

### 2.5 Retention Policy

```
SCHEDULED JOB (daily):
  cutoff = now() - 90 days
  UPDATE Notification SET archived_at = now()
  WHERE created_at < cutoff AND archived_at IS NULL

-- Archived notifications are excluded from the active list:
GET /notifications → WHERE archived_at IS NULL ORDER BY created_at DESC
-- Internal logs (platform owner access) can query all, including archived.
```

## 3. Admin Audit Log

### 3.1 Purpose

Permanent, tamper-proof record of all high-impact administrative actions. Required for institutional accountability and dispute resolution.

### 3.2 Data Model

```
AdminAuditLog
  id              UUID, primary key
  org_id          FK → Organization
  timestamp       timestamp (indexed)
  actor_id        FK → User (role = ADMIN or PLATFORM_OWNER)
  action_type     enum (see Section 3.3)
  target_type     string  -- e.g. "Student", "Educator", "Class", "Section"
  target_id       UUID    -- ID of the affected record
  details         JSON    -- action-specific payload (old/new values, reasons, etc.)
```

### 3.3 Action Types

| Action Type | Logged When |
|---|---|
| `STUDENT_PROFILE_CHANGED` | Any profile field updated (stores old + new values) |
| `ACCOUNT_STATUS_CHANGED` | Student status changes (old status, new status) |
| `MANUAL_ENROLLMENT_ADD` | Admin adds subject to student |
| `MANUAL_ENROLLMENT_REMOVE` | Admin removes subject enrollment |
| `AUTO_ENROLLED` | System enrolls student (during validation) |
| `ENROLLMENT_SKIPPED_DUPLICATE` | Duplicate enrollment silently skipped |
| `ENROLLMENT_PENDING_SECTION` | Student pending due to section capacity |
| `ENROLLMENT_PENDING_CLASS` | Student pending due to class capacity |
| `SECTION_CAPACITY_OVERFLOW` | Section full — Admin chose create/skip |
| `CLASS_CAPACITY_OVERFLOW` | Class full — Admin chose split/pending |
| `EDUCATOR_CLASS_ASSIGNED` | Educator assigned to a class |
| `EDUCATOR_CLASS_REASSIGNED` | Class reassigned to different educator |
| `EDUCATOR_REMOVED` | Educator account deactivated |
| `PASSWORD_RESET` | Password reset for one or more accounts |
| `GRADE_LOCK_OVERRIDE` | Platform owner unlocks grades |
| `GRADES_LOCKED` | Grade lock applied (manual, auto, or override) |
| `CLASS_ARCHIVED` | Class archived at end of semester |
| `CALENDAR_EVENT_CREATED` | Academic calendar event added |
| `CALENDAR_EVENT_UPDATED` | Academic calendar event modified |
| `CALENDAR_EVENT_DELETED` | Academic calendar event removed |
| `BULK_IMPORT_COMPLETED` | Bulk student import finished (with summary) |

### 3.4 Write Helper

```
FUNCTION auditLog(org_id, actor_id, action_type, target_type, target_id, details):
  CREATE AdminAuditLog {
    org_id,
    timestamp: now(),
    actor_id,
    action_type,
    target_type,
    target_id,
    details  -- JSON, action-specific
  }
```

Never update or delete audit log entries. Append-only.

### 3.5 Admin UI — Audit Log Viewer

```
GET /admin/audit-log
  Query params:
    date_from, date_to
    action_type (filter)
    target_type (filter)
    target_id (exact match — look up a specific student, class, etc.)

  Response: paginated list of log entries, newest first.
  Fields shown: timestamp, action_type, target, details summary, actor name.
```

## 4. Educator Activity Log

### 4.1 Purpose

Class-level event log scoped to each educator's classes. Educators see their own log. Admin can see all educator logs.

### 4.2 Data Model

```
EducatorActivityLog
  id              UUID, primary key
  org_id          FK → Organization
  educator_id     FK → Educator
  class_id        FK → Class
  event_type      enum (see Section 4.3)
  details         JSON
  created_at      timestamp (indexed)
```

### 4.3 Event Types

| Event Type | Logged When |
|---|---|
| `STUDENT_ENROLLED` | New student added (auto or Admin) |
| `STUDENT_REMOVED` | Student removed (educator or Admin) |
| `MEETING_STARTED` | Educator opens room |
| `MEETING_ENDED` | Educator ends meeting |
| `ASSESSMENT_CREATED` | Assessment configured and queued |
| `ASSESSMENT_EDITED` | Question or config changed |
| `ASSESSMENT_PUBLISHED` | Scores published (all or selected) |
| `ASSESSMENT_UNPUBLISHED` | Scores hidden |
| `ASSESSMENT_DELETED` | Soft-deleted assessment |
| `GRADES_LOCKED` | Grade lock applied |
| `LESSON_CREATED` | Lesson saved for first time |
| `LESSON_UPDATED` | Lesson content updated |
| `CONCEPT_EXTRACTION_TRIGGERED` | Manual re-extraction initiated |
| `CONCEPT_EXTRACTION_COMPLETED` | Background job finished |

### 4.4 Write Helper

```
FUNCTION activityLog(educator_id, class_id, event_type, details):
  CREATE EducatorActivityLog {
    org_id: getEducatorOrg(educator_id),
    educator_id,
    class_id,
    event_type,
    details,
    created_at: now()
  }
```

Never delete activity log entries.

### 4.5 Educator UI — Activity Log

Educator sees their own log per class:
```
GET /educators/{educator_id}/activity-log?class_id={class_id}
  Response: paginated log entries, newest first.
```

Admin can see all:
```
GET /admin/educator-activity-log?educator_id={id}&class_id={id}
```

## 5. Soft Delete Policy

### 5.1 What Is Soft Delete

Instead of removing a record from the database, a `deleted_at` timestamp is set. The record becomes invisible in normal queries but is permanently preserved for auditing, transcript integrity, and dispute resolution.

### 5.2 Records That Use Soft Delete

| Record Type | When Applied |
|---|---|
| `Class` | Class archived by Admin |
| `Assessment` | Educator deletes an assessment |
| `Lesson` | Educator deletes a lesson |
| `Enrollment` | Student removed from class (by educator or Admin, or status change) |
| `Meeting` | Meeting deleted (if allowed) |
| `Section` | Section removed (only if no active students) |

### 5.3 Implementation Pattern

Every soft-deletable model has:

```
deleted_at    timestamp, nullable, default null, indexed
```

All standard queries **must** include:

```sql
WHERE deleted_at IS NULL
```

Do not rely on application-layer filtering — enforce it at the query level or via a default scope in your ORM.

### 5.4 What Happens to Related Records

| Soft-deleted record | Effect on related records |
|---|---|
| `Class` archived | Enrollments remain. Grades preserved. Sessions remain. |
| `Assessment` deleted | `StudentAssessment` scores wiped (per spec). Attempts soft-deleted. |
| `Lesson` deleted | `ConceptBuild` detached (not deleted). Assessments generated from it remain. |
| `Enrollment` removed | `AttendanceRecord` rows remain. `StudentAssessment` rows remain (archived). |
| `Meeting` deleted | `MeetingChatMessage` rows are inaccessible but preserved. |

### 5.5 Hard Deletes

Hard deletes are **never performed** on:
- Classes, Assessments, Lessons, Enrollments, Meetings
- Any log record (AdminAuditLog, EducatorActivityLog, ClassOwnershipLog)
- Any grade or score record

The only hard deletes permitted:
- `AcademicCalendarEvent` (calendar events are not academic records)
- `MeetingJoinRequest` (operational metadata, no academic significance)
- Notification archive cleanup is a data management concern, not a hard delete of academic data

## 6. Build Order for This Module

Build this module **before or alongside** the other modules since every module writes to it.

```
1. Notification model + notify() helper function
2. Notification list endpoint (recipient-scoped)
3. Notification retention scheduled job (90-day archive)
4. AdminAuditLog model + auditLog() helper function
5. Admin audit log read endpoint (filterable)
6. EducatorActivityLog model + activityLog() helper function
7. Educator activity log read endpoints (educator-scoped + admin-scoped)
8. Soft delete pattern: add deleted_at to all applicable models,
   enforce WHERE deleted_at IS NULL in all queries
9. Scheduled notification jobs:
     - ASSESSMENT_RELEASED (fires at release_date)
     - ASSESSMENT_DEADLINE_APPROACHING (fires N hours before end_date)
     - MEETING_REMINDER (fires N minutes before scheduled_at,
       with calendar suppression check)
10. Admin UI: audit log viewer (filterable, paginated)
11. Educator UI: activity log viewer (per class)
```
