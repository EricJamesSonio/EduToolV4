# DEV-01 — Organization & School Setup
**EduTool Developer Guide**
> Covers: Org creation, school year lifecycle, semester settings, sections, courses/strands, academic calendar.

---

## 1. Overview

Every piece of data in EduTool lives under an **Organization**. There is exactly one Organization per Admin account. This guide covers everything needed to set up and manage the org's structural foundation before any students or educators are added.

Build this module first. All other modules depend on it.

---

## 2. Organization

### 2.1 Data Model

```
Organization
  id              UUID, primary key
  name            string, required
  handle          string, unique across platform, e.g. "collegeofmary"
  admin_id        FK → User (role = Admin), unique (one org per admin)
  created_at      timestamp
```

### 2.2 Creation Flow

- Triggered once, right after Admin first logs in.
- Admin is redirected to an org setup screen if `admin.org_id` is null.
- Admin enters `name` and `handle`.
- `handle` must be unique across the entire platform. Validate on blur and on submit.
- On save: org record is created, `admin.org_id` is set. Admin proceeds to dashboard.

### 2.3 Rules

- Handle cannot be changed after creation.
- Name can be edited by Admin at any time.
- No public-facing use of org data — it is internal only.

## 3. School Year

### 3.1 Data Model

```
SchoolYear
  id              UUID, primary key
  org_id          FK → Organization
  label           string, e.g. "2024-2025"
  start_date      date
  end_date        date
  is_active       boolean (only one active per org at a time)
  created_at      timestamp
```

### 3.2 Rules

- Only one school year can be `is_active = true` per org at a time.
- Past school years are permanently read-only once a new one is activated.
- Activating a new school year does NOT delete or alter past data.

### 3.3 What Carries Over vs. Resets

When Admin activates a new school year:

| Carries Over (unchanged) | Resets / Unlocks |
|--------------------------|------------------|
| Level sections and structure | Schedules — rebuilt fresh |
| Sections (all levels) | Subjects — unlocked for editing |
| Courses and strands | Classes — none exist yet |
| Semester setting templates | Grade locks — all start unlocked |
| Educator accounts | |
| Student accounts (with statuses) | |

> **Implementation note:** "Carrying over" means the records remain linked and readable. Classes and schedules are NOT copied — they are created fresh by Admin for the new year.

## 4. Semester Settings

### 4.1 Purpose

Semester settings are **reusable templates**. Each course or strand independently selects which template to use per school year. They define the date ranges for each semester period.

### 4.2 Data Model

```
SemesterTemplate
  id              UUID, primary key
  org_id          FK → Organization
  name            string, e.g. "June-March 3-Semester"
  created_at      timestamp

SemesterPeriod
  id              UUID, primary key
  template_id     FK → SemesterTemplate
  label           string, e.g. "1st Semester"
  order           integer (1, 2, or 3)
  start_date      date
  end_date        date
```

### 4.3 Validation Rules

- A template can have **1 to 3** semester periods.
- Period date ranges must not overlap with each other within the same template.
- Each period's `start_date` must be before its `end_date`.
- Enforce all validations server-side. Show inline errors per period on the form.

### 4.4 Usage

- When Admin configures a Course or Strand, they select a `SemesterTemplate`.
- This selection determines the available semester periods when creating classes for that course/strand.

## 5. Level Sections

Level sections are fixed system constants — they are not created by Admin. They define the top-level academic groupings.

| Value | Grade/Year Range |
|-------|-----------------|
| `ELEMENTARY` | Grade 1–6 |
| `HIGH_SCHOOL` | Grade 7–10 |
| `SENIOR_HIGH` | Grade 11–12 |
| `COLLEGE` | Year 1–N (N defined per course) |

Store as an enum. Never allow insertion or deletion by any user.

## 6. Sections

### 6.1 Purpose

Sections are named groupings of students within a specific grade/year level. They exist for all level sections.

Examples:
- Grade 3 → Section A, Section B
- Grade 8 → Narra, Molave
- Grade 11 STEM → Section 1
- BSCS Year 2 → Block A, Block B

### 6.2 Data Model

```
Section
  id              UUID, primary key
  org_id          FK → Organization
  name            string, required — fully custom, no auto-generation
  level_section   enum (ELEMENTARY | HIGH_SCHOOL | SENIOR_HIGH | COLLEGE)
  grade_year      string, e.g. "Grade 3", "Year 2", "Grade 11"
  strand_id       FK → Strand, nullable (Senior High only)
  course_id       FK → Course, nullable (College only)
  capacity        integer, nullable (null = unlimited)
  created_at      timestamp
  deleted_at      timestamp, nullable (soft delete)
```

### 6.3 Creation Rules

- Admin creates sections manually. **No auto-naming by the system.**
- Name is free text — Admin decides the naming scheme entirely.
- `strand_id` is required if `level_section = SENIOR_HIGH`.
- `course_id` is required if `level_section = COLLEGE`.
- Capacity is optional. If set, it must be a positive integer.

### 6.4 Section Capacity Enforcement

This check runs every time a student is assigned to a section (on account create or profile update).

```
FUNCTION checkSectionCapacity(section_id, student_id):

  section = getSectionById(section_id)
  IF section.capacity IS NULL:
    RETURN OK  -- unlimited

  current_count = countActiveStudentsInSection(section_id)
  IF current_count < section.capacity:
    RETURN OK

  -- Capacity hit. Prompt Admin with two options:
  PROMPT Admin:
    (A) "Create a new section"
        → Show section creation form pre-filled with:
            level_section, grade_year, strand_id, course_id, capacity
          Admin must provide a custom name.
          On save: create section, assign student to new section.
    (B) "Leave without section for now"
        → Assign student no section.
          Set student.status = PENDING.

  Log decision in Admin Audit Log:
    action_type = "SECTION_CAPACITY_OVERFLOW"
    details = { section_id, student_id, decision: A or B }
```

> **Key rule:** Never auto-generate a section name. Always require Admin input.

### 6.5 Admin UI

- Section list: filterable by level section, grade/year, strand/course.
- Each section shows current student count vs. capacity.
- Admin can rename a section at any time.
- Soft-delete a section: only allowed if no Active students are assigned.

## 7. Courses (College)

### 7.1 Data Model

```
Course
  id                UUID, primary key
  org_id            FK → Organization
  title             string, e.g. "BSCS"
  description       string, e.g. "Bachelor of Science in Computer Science"
  max_year_level    integer, e.g. 4 (how many year levels exist)
  semester_template_id  FK → SemesterTemplate
  created_at        timestamp
```

### 7.2 Rules

- `max_year_level` determines the available year levels when assigning students, creating subjects, and creating classes for this course.
- `semester_template_id` determines the semester periods available for classes under this course.
- A course cannot be deleted if any student is enrolled in it or any class references it.

### 8.1 Data Model

```
Strand

  description       string, e.g. "Science, Technology, Engineering, Mathematics"
```

- Senior High always covers Grade 11 and Grade 12 — no `max_grade` needed.
- `semester_template_id` determines semester periods for classes under this strand.
- A strand cannot be deleted if any student is enrolled in it or any class references it.

## 9. Academic Calendar

### 9.1 Purpose

The academic calendar lets Admin declare org-wide non-class days. These affect session generation, attendance, lesson week numbering, and meeting notifications.

### 9.2 Data Model

```
AcademicCalendarEvent
  id              UUID, primary key
  org_id          FK → Organization
  school_year_id  FK → SchoolYear
  title           string
  event_type      enum (HOLIDAY | NO_CLASS_DAY | EXAM_WEEK | SPECIAL_EVENT)
  start_date      date
  end_date        date  -- same as start_date for single-day events
  created_at      timestamp
  updated_at      timestamp
```

### 9.3 Event Type Behavior

| Event Type | Sessions Skipped | Week Index Preserved | Meeting Notifs Suppressed |
|---|---|---|---|
| `HOLIDAY` | Yes | Yes | Yes |
| `NO_CLASS_DAY` | Yes | Yes | Yes |
| `EXAM_WEEK` | No — advisory only | N/A | No |
| `SPECIAL_EVENT` | No — informational | N/A | No |

### 9.4 Session Generation Integration

When generating class sessions (see DEV-05), check every candidate date against the Academic Calendar:

```
FUNCTION isSessionDay(date, org_id, school_year_id):
  events = getCalendarEvents(org_id, school_year_id,
             types: [HOLIDAY, NO_CLASS_DAY],
             overlapping: date)
  IF events.length > 0:
    RETURN false  -- skip this date, do not create session record
  RETURN true
```

Sessions that are skipped do not consume a week index. The next valid session picks up the sequence.

### 9.5 Retroactive Events

If Admin adds a calendar event after sessions have already been generated:
- Warn Admin: "Sessions already exist on some of these dates. Past records may need manual review."
- Do NOT auto-delete existing session records. Admin reviews manually.
- Future sessions (not yet generated) will respect the new event.

### 9.6 Admin UI

- Calendar view showing existing events for the active school year.
- Create / edit / delete events.
- Delete is a hard delete — calendar events are not academic records and do not need soft deletion.

Build in this exact order to avoid dependency issues:
