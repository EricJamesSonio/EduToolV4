### Cross-Module Calls

**On student account save (create or update):**
You must call the enrollment validation sequence from DEV-03. Do not duplicate that logic here — import and call it.

```

  - Section capacity check (which calls DEV-01's section capacity logic)
  - Class matching + auto-enrollment (which calls DEV-05's enrollMatchingClasses)
  - Duplicate enrollment prevention
  - PendingEnrollment creation if capacity is hit
```

**On bulk import (DEV-02 Section 7):**
Same as above — after each student account is created from the CSV, call `EnrollmentValidationService.runForStudent(studentId)` for that student. This means session generation (DEV-05) and attendance record creation (DEV-08) also fire as part of that chain.

**On student status → DROPPED or TRANSFERRED:**
You must call the unenrollment side-effect defined in DEV-03 Section 2.3.

```
After status change to DROPPED or TRANSFERRED:
  → call EnrollmentService.unenrollAllActive(studentId)
     This soft-deletes all active Enrollment records for the student.
     This also triggers educator notifications via DEV-11's NotificationService.
```

**Dependencies you must have built before this module works end-to-end:**
- DEV-01 (org, section, course, strand must exist before student profiles can reference them)
- DEV-11 (NotificationService and AuditLogService must exist before account creation can log anything)

# DEV-02 — Account Management
**EduTool Developer Guide**
> Covers: User roles, Admin provisioning, educator account creation, student account creation, account statuses, password management, credential export, bulk student import.

---

## 1. Overview

EduTool has three roles: **Admin**, **Educator**, and **Student**. No self-registration exists at any level. The platform owner creates Admin accounts manually. Admins create all Educator and Student accounts within their org.

This guide covers everything about creating, managing, and distributing accounts. For student enrollment logic triggered by account creation, see DEV-03.

---

## 2. User Model

```
User
  id              UUID, primary key
  org_id          FK → Organization, nullable (null for platform owner only)
  role            enum (PLATFORM_OWNER | ADMIN | EDUCATOR | STUDENT)
  full_name       string, required
  email           string, unique across platform, required
  password_hash   string
  generated_password  string, stored temporarily for credential export
  created_at      timestamp
  last_login_at   timestamp, nullable
```

> **Security note:** `generated_password` is the plaintext password stored only until the Admin downloads credentials. After the first login by the user, this field should be cleared. Never expose it in API responses except in the credential export endpoint (Admin only).

---

## 3. Educator Accounts

### 3.1 Data Model

```
Educator
  id              UUID, primary key (also the Educator ID shown in UI)
  user_id         FK → User (role = EDUCATOR)
  org_id          FK → Organization
  educator_code   string, unique within org, system-generated
                  format: EDU-{4-digit-random}, e.g. EDU-4821
  created_at      timestamp
```

### 3.2 Creation Flow

Admin fills:
- Full Name
- Email (school-provided Gmail)

On save:
1. Validate email is unique across the platform.
2. Generate a 10-character alphanumeric password.
3. Create `User` record with `role = EDUCATOR`.
4. Create `Educator` record with a unique `educator_code`.
5. Store plaintext password in `user.generated_password` for credential export.
6. Return success. Educator appears in Admin's educator list.

### 3.3 Educator Search

Admin can search educators by:
- `educator_code` (exact or partial match)
- `full_name` (case-insensitive partial match)

From the educator detail view, Admin can:
- View profile and `educator_code`
- See all classes currently assigned to this educator
- Add a class assignment
- Remove a class assignment (with reassignment flow if class is active — see DEV-04)
- Reset password

## 4. Student Accounts

### 4.1 Data Model

```
Student
  id              UUID, primary key
  user_id         FK → User (role = STUDENT)
  org_id          FK → Organization
  student_id      string, Admin-assigned, unique within org
                  e.g. "2024-0001"
  level_section   enum (ELEMENTARY | HIGH_SCHOOL | SENIOR_HIGH | COLLEGE)
  grade_year      string, e.g. "Grade 3", "Year 2", "Grade 11"
  section_id      FK → Section, nullable
  strand_id       FK → Strand, nullable (Senior High only)
  course_id       FK → Course, nullable (College only)
  status          enum (ACTIVE | PENDING | DROPPED | TRANSFERRED |
                        SUSPENDED | GRADUATED)
  status_changed_at   timestamp
  created_at      timestamp
```

### 4.2 Creation Form — Dynamic Field Rules

The form adapts based on the selected `level_section`:

| Level Section | Required Fields | Conditional Fields |
|---|---|---|
| ELEMENTARY | grade_year, section | — |
| HIGH_SCHOOL | grade_year, section | — |
| SENIOR_HIGH | grade_year, strand | section (optional) |
| COLLEGE | grade_year, course | section (optional) |

- `grade_year` options come from the selected level section's structure.
  - ELEMENTARY: Grade 1–6
  - HIGH_SCHOOL: Grade 7–10
  - SENIOR_HIGH: Grade 11–12
  - COLLEGE: Year 1–N where N = `course.max_year_level`
- `section` dropdown shows only sections matching `level_section + grade_year + strand/course`.
- `strand` dropdown shows only strands in the org.
- `course` dropdown shows only courses in the org.
- No hardcoded values — all options fetched from org data.

### 4.3 On Save — Validation Sequence

When Admin saves a student profile (create or update), run these checks in order. Stop at the first blocking issue and prompt Admin.

```
STEP 1 — Section Capacity Check (if section_id is set)
  → See DEV-01 Section 6.4 for full flow.
  Outcome A: Section has space → proceed to Step 2.
  Outcome B: Section full, Admin creates new section → proceed to Step 2 with new section.
  Outcome C: Section full, Admin declines → student saved with section_id = null,
             status = PENDING. Stop here. Log to Admin Audit Log.

STEP 2 — Auto-Enrollment (if status = ACTIVE after Step 1)
  → See DEV-05 Section 4 for full auto-enrollment engine.
  For each matching class:
    Outcome A: Capacity available → enroll student. Log.
    Outcome B: Class full, Admin splits → enroll in new class. Log.
    Outcome C: Class full, Admin declines → mark student as
               Pending Enrollment for that subject. Log.
    Outcome D: Duplicate enrollment → skip silently. Log.

STEP 3 — Complete
  Student record saved. Log all outcomes to Admin Audit Log.
```

### 4.4 Student Account Status

| Status | Access | Auto-Enrollment | Enrollments |
|---|---|---|---|
| `ACTIVE` | Full access | Yes | Enrolled normally |
| `PENDING` | No access | No | None until resolved |
| `DROPPED` | No access (read-only) | No | All removed |
| `TRANSFERRED` | No access (read-only) | No | All removed |
| `SUSPENDED` | No access | No | Retained but inaccessible |
| `GRADUATED` | No access (read-only) | No | Archived |

**Status transition rules:**

- `PENDING → ACTIVE`: Admin resolves section + enrollment conflicts manually.
- `SUSPENDED → ACTIVE`: Admin lifts suspension directly.
- `ACTIVE → SUSPENDED`: Admin sets directly.
- `ACTIVE / SUSPENDED → DROPPED`: Admin sets. Triggers unenrollment from all active classes. **Irreversible without platform owner.**
- `ACTIVE / SUSPENDED → TRANSFERRED`: Same as DROPPED.
- `GRADUATED`: Set by system when student reaches `course.max_year_level` or equivalent. **Irreversible without platform owner.**
- `DROPPED / TRANSFERRED / GRADUATED → ACTIVE`: Requires platform owner action. Logged permanently.

When status changes to `DROPPED` or `TRANSFERRED`:
1. Find all active class enrollments for this student.
2. Soft-delete each enrollment record (`deleted_at = now()`).
3. Notify affected educators: "Student [Name] has been removed from your class [Title] due to status change."
4. Log all unenrollments in Admin Audit Log.

### 4.5 Student Search

Admin can search students by:
- `student_id` (exact or partial match)
- `full_name` (case-insensitive partial match)
- `status` filter
- `level_section`, `grade_year`, `section`, `strand`, `course` filters

All filters are combinable. Results paginated (100 per page minimum for large orgs).

From the student detail view, Admin can:
- View full profile + current status
- See all current class enrollments (subject, educator, semester)
- Add an additional subject (see DEV-03)
- Remove a subject enrollment (see DEV-03)
- Change account status
- Edit profile (only between semesters — enforce this)
- Reset password

## 5. Password Management

### 5.1 Rules

- Educators and students **cannot change their own passwords.** The password field is never exposed to them.
- Only Admin can reset passwords.
- On reset: generate a new 10-character alphanumeric password. Replace `password_hash` and `generated_password`. The old password is immediately invalid.

### 5.2 Reset Scope

Admin can reset passwords for:
- All educator accounts in the org
- All student accounts in the org
- Both at once
- Selected specific accounts (multi-select in account list)

### 5.3 Flow

```
1. Admin selects scope (all educators / all students / both / selected).
2. Confirm dialog: "This will invalidate all current passwords for [N] accounts.
   Users will not be able to log in until they receive new credentials. Proceed?"
3. Admin confirms.
4. System generates new passwords for all accounts in scope.
5. Updates password_hash and generated_password for each.
6. Logs each reset in Admin Audit Log:
     action_type = "PASSWORD_RESET"
     target_entity = user_id
     details = { scope, reset_by: admin_id }
7. New credentials available for download via credential export (Section 6).
```

## 6. Credential Export

### 6.1 Format

Single CSV download covering all accounts in scope.

**Columns:**
```
Full Name | Student ID / Educator ID | Email | Generated Password |
Level Section | Section | Course/Strand | Year/Grade Level | Account Status
```

- Educator rows: `Student ID` column is empty. `Educator Code` goes in that column instead (or use a separate `Educator Code` column — keep consistent with your UI).
- Student rows: all columns filled.

### 6.2 Export Endpoint

- `GET /admin/credentials/export?type=all|students|educators`
- Returns a CSV file attachment.
- Only accessible by Admin role.
- Only returns accounts belonging to `admin.org_id`.

> **Security:** Never expose `generated_password` in any other endpoint. This export is the only place it appears.

## 7. Bulk Student Import

### 7.1 Purpose

For large schools (1,000+ students), Admin uploads a CSV instead of creating accounts one by one.

### 7.2 CSV Template Columns

```
full_name* | student_id* | email* | level_section* | grade_year* |
section | strand | course
```

`*` = required. `section`, `strand`, `course` are conditional on `level_section`.

Provide a downloadable blank template via: `GET /admin/students/import/template`

### 7.3 Import Flow

```
PHASE 1 — Upload & Parse
  POST /admin/students/import  (multipart, CSV file)
  Parse CSV rows into memory.
  Do not create any records yet.

PHASE 2 — Validation (row by row)
  For each row, check:
    [ ] full_name not empty
    [ ] student_id not empty
    [ ] student_id not already in org
    [ ] email not empty
    [ ] email not already in platform
    [ ] level_section is a valid enum value
    [ ] grade_year is valid for the given level_section
    [ ] section (if provided) exists in org for that level_section + grade_year
    [ ] strand (if level_section = SENIOR_HIGH) exists in org
    [ ] course (if level_section = COLLEGE) exists in org

  Produce a validation report:
    {
      valid_rows: [ ...rows ],
      error_rows: [
        { row_number: 4, student_id: "2024-001", error: "Student ID already exists" },
        { row_number: 9, student_id: "2024-006", error: "Section 'Narra' not found for Grade 7" },
        ...
      ]
    }

PHASE 3 — Admin Reviews Report
  Show report in UI before creating anything.
  Admin options:
    (A) "Fix errors and re-upload" → discard session, Admin downloads error list
    (B) "Import valid rows only ([N] accounts)" → proceed with valid rows only

PHASE 4 — Account Creation (valid rows only)
  For each valid row:
    1. Generate 10-character password.
    2. Create User record (role = STUDENT).
    3. Create Student record with status = ACTIVE.
    4. Log creation in Admin Audit Log.

PHASE 5 — Enrollment Validation
  For each newly created student, run the enrollment validation sequence
  (same as Section 4.3 above: section capacity → auto-enrollment → duplicate check).
  Capacity conflicts produce Pending students — Admin resolves after import.

PHASE 6 — Credentials Available
  All imported student credentials available for download immediately:
  GET /admin/students/import/{import_job_id}/credentials
  Returns CSV with the same columns as the standard credential export.

PHASE 7 — Post-Import Summary
  Show Admin:
    - N accounts created successfully
    - N students pending (capacity conflicts)
    - N rows skipped (errors)
    - Download credentials button
    - Resolve pending students button
```

### 7.4 Rules

- Bulk import creates **student accounts only.** Educator accounts are always created individually.
- All validation rules (section capacity, class capacity, duplicate enrollment) still apply per student. Import does not bypass any of them.
- Capacity conflicts after import surface as Pending students. Admin must resolve them manually.
- A failed import (all rows invalid) creates zero records.
