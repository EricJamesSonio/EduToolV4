## ADD TO: DEV-02 — Account Management

### Cross-Module Calls

**On student account save (create or update):**
You must call the enrollment validation sequence from DEV-03. Do not duplicate that logic here — import and call it.

```
After saving Student record:
  → call EnrollmentValidationService.runForStudent(studentId)
     (defined in DEV-03, Section 3)

This service handles:
  - Section capacity check (which calls DEV-01's section capacity logic)
  - Class matching + auto-enrollment (which calls DEV-05's enrollMatchingClasses)
  - Duplicate enrollment prevention
  - PendingEnrollment creation if capacity is hit
```

**On bulk import (DEV-02 Section 7):**
Same as above — after each student account is created from the CSV, call `EnrollmentValidationService.runForStudent(studentId)` for that student. This means session generation (DEV-05) and attendance record creation (DEV-08) also fire as part of that chain.

**On student status → DROPPED or TRANSFERRED:**
You must call the unenrollment side-effect defined in DEV-03 Section 2.3.

```
After status change to DROPPED or TRANSFERRED:
  → call EnrollmentService.unenrollAllActive(studentId)
     This soft-deletes all active Enrollment records for the student.
     This also triggers educator notifications via DEV-11's NotificationService.
```

**Dependencies you must have built before this module works end-to-end:**
- DEV-01 (org, section, course, strand must exist before student profiles can reference them)
- DEV-11 (NotificationService and AuditLogService must exist before account creation can log anything)
- DEV-03 EnrollmentValidationService (must be built before student save is complete)
- DEV-05 auto-enrollment engine (must exist before EnrollmentValidationService can call it)

## ADD TO: DEV-03 — Student Management

### Cross-Module Calls

**EnrollmentValidationService — this is the shared service called by DEV-02 and DEV-05**

Build `EnrollmentValidationService` as a standalone injectable service (not tied to a controller). Both DEV-02 (account creation) and DEV-05 (class creation) call it.

```
EnrollmentValidationService.runForStudent(studentId):
  Step 1 → Check section capacity
           If hit: calls DEV-01 SectionService.handleCapacityOverflow()
  Step 2 → Find matching classes
           Calls DEV-05 ClassService.getMatchingClasses(student)
           For each match: calls DEV-05 EnrollmentService.enroll(studentId, classId)
  Step 3 → Duplicate check (inside EnrollmentService.enroll)

EnrollmentService.enroll(studentId, classId):
  - Creates Enrollment record
  - Calls DEV-08 AttendanceService.createRecordsForStudent(studentId, classId)
    (attendance records must be created at the moment of enrollment)
  - Calls DEV-09 GradeService.lockRubricIfNeeded(classId)
    (rubric locks on first enrollment)
  - Calls DEV-11 NotificationService.notify(educatorUserId, STUDENT_ADDED_TO_CLASS)
  - Calls DEV-11 AuditLogService.log(AUTO_ENROLLED)
```

**On profile update (re-enrollment trigger):**

```
When level_section, grade_year, section_id, strand_id, or course_id changes:
  Step 1 → Find all active enrollments for this student
  Step 2 → For each enrollment where class no longer matches new profile:
             → call EnrollmentService.unenroll(studentId, classId)
               which soft-deletes Enrollment
               and notifies educator (DEV-11)
               and logs (DEV-11)
  Step 3 → call EnrollmentValidationService.runForStudent(studentId)
             with the new profile (re-enroll in newly matching classes)
```

**Transcript query:**
The transcript read in DEV-03 Section 7 reads from:
- `Enrollment` table (including soft-deleted where grade was locked)
- `StudentGrade` table (DEV-09)
- `Class` table (DEV-05)
- `ClassOwnershipLog` (DEV-04) — to get educator name at finalization time

You need DEV-04, DEV-05, DEV-09 fully built before transcript is complete.

**Dependencies you must have built before this module works end-to-end:**
- DEV-01 (sections, courses, strands)
- DEV-05 (Class model, EnrollmentService, getMatchingClasses)
- DEV-08 (AttendanceService.createRecordsForStudent)
- DEV-09 (GradeService.lockRubricIfNeeded)
- DEV-11 (NotificationService, AuditLogService)

## ADD TO: DEV-04 — Educator Management

### Cross-Module Calls

**On educator class reassignment:**

```
When Admin reassigns a class to a new educator:
  → Reads all class data from DEV-05 (Class, Lessons, Assessments)
    — no data moves, educator_id on the Class record just changes
  → Creates ClassOwnershipLog entry (DEV-04's own table)
  → Calls DEV-11 NotificationService.notify(newEducatorUserId, CLASS_REASSIGNED)
  → Calls DEV-11 AuditLogService.log(EDUCATOR_CLASS_REASSIGNED)

Nothing in DEV-06, DEV-07, DEV-08, DEV-09 needs to change on reassignment.
The new educator inherits everything by just being the class's educator_id.
```

**GradeRecord attribution (DEV-09 dependency):**
DEV-09 stores `graded_by_educator_id` on each score record. When you build DEV-09's grading endpoint, pull the `educator_id` from the currently authenticated user at the time of grading — not from `class.educator_id`. This is what preserves attribution after reassignment.

```
// In DEV-09 grade save endpoint:
graded_by_educator_id = currentUser.educatorId  // from JWT, not from class
```

Make sure this field exists in the DEV-09 data model before building reassignment — it's what makes the ownership log meaningful.

**On educator removal:**

```
Before allowing removal:
  → Query DEV-05 ClassService.getActiveClassesForEducator(educatorId)
  If any active classes exist: block removal, show list.
  If none: proceed with soft-disable (user.is_active = false)
  → Calls DEV-11 AuditLogService.log(EDUCATOR_REMOVED)
```

**Dependencies you must have built before this module works end-to-end:**
- DEV-05 (Class model — needed to check active class assignments)
- DEV-09 (GradeRecord.graded_by_educator_id must exist before first grade is saved)
- DEV-11 (NotificationService, AuditLogService)

## ADD TO: DEV-05 — Class & Subject Management

### Cross-Module Calls

**On class creation — immediately after saving the Class record:**

```
1. → call EnrollmentValidationService.runForClass(classId)
      (defined in DEV-03, same service — just direction is reversed:
       find matching students and enroll them)

   EnrollmentValidationService.runForClass(classId):
     → gets all Active students matching this class's profile
     → for each: calls EnrollmentService.enroll(studentId, classId)
       which internally calls:
         DEV-08 AttendanceService.createRecordsForSession (for each session)
         DEV-09 GradeService.lockRubricIfNeeded(classId)
         DEV-11 NotificationService + AuditLogService

2. → call SessionGenerationService.generateSessions(classId)
      (DEV-05's own service — but reads AcademicCalendar from DEV-01)

   After generating sessions:
     → for each session created:
       → call DEV-08 AttendanceService.createAttendanceRecordsForSession(sessionId)
```

**On EnrollmentService.enroll() — calls out to three other modules:**

```
EnrollmentService.enroll(studentId, classId):
  → CREATE Enrollment record
  → DEV-08: AttendanceService.createRecordsForStudent(studentId, classId)
  → DEV-09: GradeService.lockRubricIfNeeded(classId)
  → DEV-11: NotificationService.notify(educatorUserId, STUDENT_ADDED_TO_CLASS)
  → DEV-11: AuditLogService.log(AUTO_ENROLLED)
```

**Session generation reads Academic Calendar from DEV-01:**

```
SessionGenerationService.generateSessions(classId):
  → reads AcademicCalendarEvent records (DEV-01)
    to skip HOLIDAY and NO_CLASS_DAY dates
  → for each valid session created:
    → DEV-08: AttendanceService.createAttendanceRecordsForSession(sessionId)
```

**On class archive:**

```
ClassService.archiveClass(classId):
  → checks if any grades are unlocked
  → if so: calls DEV-09 GradeService.lockGrades(classId, locked_by: ADMIN)
    (which triggers score auto-publish + student notifications)
  → sets class.is_archived = true, class.deletedAt = now()
  → DEV-11: AuditLogService.log(CLASS_ARCHIVED)
```

**Dependencies you must have built before this module works end-to-end:**
- DEV-01 (AcademicCalendarEvent — needed for session generation)
- DEV-03 EnrollmentValidationService (needed on class creation)
- DEV-08 AttendanceService (needed on session creation + enrollment)
- DEV-09 GradeService.lockRubricIfNeeded (needed on first enrollment)
- DEV-11 (NotificationService, AuditLogService)

## ADD TO: DEV-06 — Lesson Management

### Cross-Module Calls

**Lesson is scoped to a Class — before creating a lesson:**

```
Before saving a Lesson:
  → verify class exists and educator owns it
    → DEV-05 ClassService.getClassForEducator(classId, educatorId)
  → verify week_session_id belongs to this classId
    → DEV-05 ClassSession must exist for this assignment
```

**On first lesson save (concept extraction auto-trigger):**

```
After lesson is saved with detail.wordCount >= 10 AND hasConceptBuild = false:
  → call ConceptExtractionService.trigger(lessonId, AUTO)
    This queues a BullMQ job.
    On job complete:
      → DEV-11: NotificationService.notify(educatorUserId, CONCEPT_EXTRACTION_COMPLETE)
      → DEV-11: ActivityLogService.log(CONCEPT_EXTRACTION_COMPLETED)
```

**Presentation mode (DEV-10 dependency):**

```
Lesson presentation is driven by DEV-10's MeetingGateway (Socket.IO).
DEV-06 only provides the lesson data.
DEV-10 handles the WebSocket events: PRESENT_LESSON, LESSON_NAVIGATE.

You need DEV-10's MeetingGateway built before presentation mode works.
DEV-06 itself has no Socket.IO code — it just exposes:
  GET /lessons/:id  →  returns lesson content for the gateway to push
```

**Dependencies you must have built before this module works end-to-end:**
- DEV-05 (Class + ClassSession must exist — lessons attach to sessions)
- DEV-11 (NotificationService, ActivityLogService)
- DEV-10 (for presentation mode only — can defer until DEV-10 is built)

## ADD TO: DEV-07 — Assessment Management

### Cross-Module Calls

**Assessment is scoped to a Class and a Lesson — before creating:**

```
Before saving an Assessment:
  → verify lesson.classId = the educator's class (DEV-05)
  → verify lesson.conceptBuildId exists and status = COMPLETE (DEV-06)
    If not: block with "No complete concept build for this lesson."
```

**On assessment submission — calls DEV-08:**

```
Inside AssessmentService.submitAssessment(attemptId):
  After updating attempt.status = SUBMITTED:
  → call DEV-08: AttendanceService.autoMarkAttendance(studentId, assessmentId)
    (marks student Present for the session on the day of submission)
```

**On assessment deletion — calls DEV-09:**

```
Inside AssessmentService.deleteAssessment(assessmentId):
  After soft-deleting the assessment:
  → call DEV-09: GradeService.triggerRecompute(classId)
    (final grades must recompute without the deleted assessment's scores)
```

**On score publish — calls DEV-11:**

```
When educator publishes scores (all or selected):
  → for each student whose score_published flips to true:
    → DEV-11: NotificationService.notify(studentUserId, SCORE_PUBLISHED)
```

**On grade lock (called FROM DEV-09, not initiated here):**

```
DEV-09's lockGrades() calls:
  UPDATE StudentAssessment SET score_published = true
  WHERE assessment_id IN class's assessments

This is DEV-09's responsibility to trigger — DEV-07 does not initiate it.
DEV-07 just owns the StudentAssessment table that DEV-09 updates.
Make sure StudentAssessment.score_published field exists in your schema.
```

**Dependencies you must have built before this module works end-to-end:**
- DEV-05 (Class model — assessments belong to classes)
- DEV-06 (ConceptBuild must exist and be COMPLETE before generation)
- DEV-08 (AttendanceService.autoMarkAttendance — called on submission)
- DEV-09 (GradeService.triggerRecompute — called on deletion)
- DEV-11 (NotificationService for score publish, ActivityLogService)

## ADD TO: DEV-08 — Attendance Management

### Cross-Module Calls

**This module is called by DEV-05 and DEV-07 — it does not initiate those calls.**

The two entry points into DEV-08 from other modules are:

```
Entry point 1 — called by DEV-05 SessionGenerationService:
  AttendanceService.createAttendanceRecordsForSession(sessionId)
  → creates one AttendanceRecord per enrolled student for that session
  → only call this AFTER Enrollment records exist for the class

Entry point 2 — called by DEV-05 EnrollmentService.enroll():
  AttendanceService.createRecordsForStudent(studentId, classId)
  → creates records for all future sessions of this class
  → call this at the moment of enrollment

Entry point 3 — called by DEV-07 AssessmentService.submitAssessment():
  AttendanceService.autoMarkAttendance(studentId, assessmentId)
  → finds the ClassSession for the submission date
  → marks record PRESENT (source = AUTO) if not already manually set
```

**Reading ClassSession — DEV-05 dependency:**

```
autoMarkAttendance needs to look up:
  ClassSession WHERE class_id = assessment.class_id AND date = DATE(submittedAt)

This query hits the ClassSession table owned by DEV-05.
Make sure ClassSession is queryable by (classId + date) — add a DB index on these two columns.
```

**Grade lock guard:**

```
setAttendance() (manual entry) must check:
  → DEV-09: GradeService.isClassLocked(classId)
  If locked: throw GradesLockedException
```

**Dependencies you must have built before this module works end-to-end:**
- DEV-05 (ClassSession table + Enrollment table must exist)
- DEV-07 (calls autoMarkAttendance on submission — DEV-08 must exist first)
- DEV-09 (grade lock check in manual attendance entry)

## ADD TO: DEV-09 — Grade Management

### Cross-Module Calls

**Rubric lock — called by DEV-05 EnrollmentService:**

```
GradeService.lockRubricIfNeeded(classId):
  → Called every time a student is enrolled (from DEV-05 EnrollmentService.enroll)
  → Checks if ClassRubric is already locked
  → If not locked AND enrollment count >= 1: locks it
  → This means DEV-05 must inject/call GradeService at enrollment time
```

**Grade computation reads from DEV-07:**

```
computeAssessmentLinkedScore(classId, studentId, category):
  → queries StudentAssessment table (DEV-07)
  → queries EssayGrade table (DEV-07)
  These tables are owned by DEV-07.
  DEV-09 reads them — it does not write to them.
  Make sure DEV-07 is built before grade computation runs.
```

**triggerRecompute — called by DEV-07 on assessment deletion:**

```
GradeService.triggerRecompute(classId):
  → called by DEV-07 when an assessment is deleted
  → recalculates StudentGrade for all enrolled students in classId
  → does NOT re-lock — only updates the computed values if grades are not yet locked
  → if grades are already locked: do nothing (locked grades are immutable)
```

**On grade lock — writes to DEV-07 and DEV-11:**

```
GradeService.lockGrades(classId):
  → UPDATE StudentAssessment SET score_published = true
    (table owned by DEV-07 — DEV-09 writes to it at lock time)
  → DEV-11: NotificationService.notify each student: GRADES_LOCKED
  → DEV-11: ActivityLogService.log(GRADES_LOCKED)
  → DEV-11: AuditLogService.log(GRADES_LOCKED)

Also locks GradingScale if this is the first lock for this level section
in the current school year (DEV-01's GradingScale table — DEV-09 writes to it).
```

**Grading scale lookup — DEV-01 dependency:**

```
matchGradingScale(levelSection, percentage):
  → queries GradingScaleEntry table (DEV-01)
  DEV-01 must have GradingScale and GradingScaleEntry tables built
  before DEV-09's computeFinalGrade() can return a grade value.
```

**PDF class card — reads educator attribution from DEV-04:**

```
Class card PDF includes educator name at time of finalization.
  → queries ClassOwnershipLog (DEV-04) to find who was the educator
    when grades were locked (locked_at timestamp)
  DEV-04 must be built before class card export works correctly.
```

**Dependencies you must have built before this module works end-to-end:**
- DEV-01 (GradingScale + GradingScaleEntry tables)
- DEV-04 (ClassOwnershipLog — for PDF class card educator attribution)
- DEV-05 (Class + Enrollment — to get enrolled students for grade computation)
- DEV-07 (StudentAssessment + EssayGrade — grade computation reads these)
- DEV-11 (NotificationService, AuditLogService, ActivityLogService)

## ADD TO: DEV-10 — Meeting Management

### Cross-Module Calls

**Meeting is scoped to a Class:**

```
Before creating a meeting:
  → verify class exists and educator owns it
    → DEV-05 ClassService.getClassForEducator(classId, educatorId)
```

**Meeting invite list reads from DEV-05 Enrollment:**

```
If invite_type = ALL:
  → query Enrollment WHERE classId AND deletedAt IS NULL
    (table owned by DEV-05)
  → create MeetingInvite for each enrolled student
```

**Academic Calendar suppression — DEV-01 dependency:**

```
On meeting creation:
  → check DEV-01 AcademicCalendarEvent for scheduled_at date
    types: [HOLIDAY, NO_CLASS_DAY]
  → if match: warn educator (do not block)

On meeting reminder job:
  → same check before sending reminder notifications
  → if calendar event on that date: skip notification
```

**Lesson presentation — DEV-06 dependency:**

```
MeetingGateway handles: { event: 'PRESENT_LESSON', lessonId }
  → fetches lesson content from DEV-06 LessonService.getLessonContent(lessonId)
  → pushes content to all room participants via Socket.IO
  → subsequent LESSON_NAVIGATE events do not need DB calls
    (content is already in memory/client)

DEV-06 does not contain Socket.IO code.
DEV-10 owns all real-time events. DEV-06 just provides the data.
```

**Notifications — DEV-11:**

```
On meeting created:
  → DEV-11: NotificationService.notify each invited student: MEETING_CREATED
On meeting reminder:
  → DEV-11: NotificationService.notify each invited student: MEETING_REMINDER
    (only if not a calendar event day)
On educator ends meeting:
  → DEV-11: ActivityLogService.log(MEETING_ENDED)
```

**Dependencies you must have built before this module works end-to-end:**
- DEV-01 (AcademicCalendarEvent — calendar suppression check)
- DEV-05 (Class + Enrollment — invite list + class ownership check)
- DEV-06 (LessonService.getLessonContent — for presentation mode)
- DEV-11 (NotificationService, ActivityLogService)

## ADD TO: DEV-11 — Notifications, Audit Logs & Soft Delete

### Cross-Module Calls

**DEV-11 is called by everyone — it calls no one.**

DEV-11 is the only module with zero outbound dependencies. Every other module writes to it. It never reads from or calls other modules.

Build DEV-11 first. The three helpers must be globally injectable before anything else is built:

```
NotificationService.notify(recipientUserId, type, message, entityType?, entityId?)
AuditLogService.log(orgId, actorId, actionType, targetType, targetId, details)
ActivityLogService.log(educatorId, classId, eventType, details)
```

**Notification scheduled jobs read from other modules:**

```
ASSESSMENT_RELEASED job:
  → queries Assessment WHERE release_date <= now() AND status != RELEASED
    (DEV-07's Assessment table)
  → for each: notifies assigned students + updates assessment status

ASSESSMENT_DEADLINE_APPROACHING job:
  → queries Assessment WHERE end_date between (now + N hours)
    (DEV-07's Assessment table)
  → for each: notifies assigned students

MEETING_REMINDER job:
  → queries Meeting WHERE scheduled_at between (now + 15min)
    (DEV-10's Meeting table)
  → checks AcademicCalendarEvent (DEV-01) — skip if holiday
  → notifies invited students

GRADE_AUTOLOCK job:
  → queries GradeLockWindow WHERE deadline <= now (DEV-09's table)
  → calls DEV-09 GradeService.lockGrades() for each unlocked class

ASSESSMENT_AUTOCLOSE job:
  → queries Assessment WHERE end_date <= now AND status = RELEASED (DEV-07)
  → closes active attempts, marks drafts as NULL

NOTIFICATION_RETENTION job:
  → self-contained — only touches Notification table (own table)
```

These jobs live in the `jobs/` folder (DEV-00B structure), not inside DEV-11 itself. But they import from DEV-11's notification service and from the relevant module services.

## Dependency Graph (quick reference)

Read this before starting any module. The arrows mean "must exist first."

```
DEV-11  ←────────────────── everything writes to it
  ↑ (built first, no deps)

DEV-01  ←── DEV-02, DEV-03, DEV-05, DEV-09, DEV-10
  (org structure — everything references it)

DEV-02  ←── (needs DEV-01, DEV-11, DEV-03's enrollment service, DEV-05's enrollment engine)

DEV-05  ←── DEV-03 (enrollment service), DEV-08 (attendance), DEV-09 (rubric lock), DEV-11
  (class creation triggers all three)

DEV-03  ←── DEV-05 (class matching), DEV-08 (attendance on enroll), DEV-09 (rubric lock), DEV-11

DEV-04  ←── DEV-05 (active class check), DEV-09 (grade attribution), DEV-11

DEV-06  ←── DEV-05 (class + session), DEV-11

DEV-07  ←── DEV-05 (class), DEV-06 (concept build), DEV-08 (auto-attendance), DEV-09 (recompute), DEV-11

DEV-08  ←── DEV-05 (session + enrollment), DEV-09 (grade lock check)
  (called BY DEV-05 and DEV-07 — has no outbound calls except to DEV-09 for lock check)

DEV-09  ←── DEV-01 (grading scale), DEV-04 (class card attribution),
             DEV-05 (enrollment), DEV-07 (assessment scores), DEV-11

DEV-10  ←── DEV-01 (calendar), DEV-05 (class + enrollment), DEV-06 (lesson content), DEV-11
```

### Safe build order that respects all dependencies

```
1. DEV-11  (no deps — build first)
2. DEV-01  (org structure — only needs DEV-11)
3. DEV-02  (accounts — needs DEV-01, DEV-11; enrollment validation built in step 5)
4. DEV-05  (class + sessions — needs DEV-01, DEV-11; calls DEV-08 + DEV-09 which come after)
           NOTE: build Class model and session generation now.
                 Leave enrollment engine incomplete until DEV-08 + DEV-09 exist.
5. DEV-03  (enrollment validation service — needs DEV-05 class model)
           After this: go back and complete DEV-02's enrollment call + DEV-05's enrollment engine.
6. DEV-04  (educator management — needs DEV-05 class model)
7. DEV-08  (attendance — needs DEV-05 sessions + enrollment)
           After this: go back and wire DEV-05 EnrollmentService → DEV-08.
8. DEV-09  (grades — needs DEV-01 scale, DEV-05 enrollment, DEV-07 scores)
           Build rubric + lockRubricIfNeeded now.
           Leave grade computation incomplete until DEV-07 exists.
           After this: wire DEV-05 EnrollmentService → DEV-09 lockRubricIfNeeded.
9. DEV-06  (lessons — needs DEV-05 sessions)
10. DEV-07 (assessments — needs DEV-06 concept build, DEV-08, DEV-09)
           After this: complete DEV-09 grade computation (it reads DEV-07 tables).
11. DEV-10 (meetings — needs DEV-05, DEV-06, DEV-01, DEV-11)
```
