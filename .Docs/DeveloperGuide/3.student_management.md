## 1. Overview

This guide covers everything Admin does with a student **after** the account exists. It assumes the account has already been created (see DEV-02). This includes profile updates, changing statuses, manually adjusting subject enrollments, and viewing the student's transcript.

The enrollment validation engine (triggered on every profile save) is defined here in full detail.

---

## 2. Profile Editing

### 2.1 When It's Allowed

Student profile changes are only allowed **between semesters**. The system must enforce this.

```
FUNCTION canEditStudentProfile(student_id):
  active_classes = getActiveClassEnrollments(student_id)
  -- "Active" means the semester is currently running (today is between
  --  semester start_date and end_date)
  IF active_classes.length > 0:
    RETURN false  -- profile locked during active semester
  RETURN true
```

If Admin tries to edit during an active semester, show: "Student profile cannot be edited while a semester is in progress. Wait until the current semester ends."

### 2.2 Editable Fields

| Field | Notes |
|---|---|
| `full_name` | Always editable |
| `email` | Always editable. Must remain unique on platform |
| `student_id` | Always editable. Must remain unique within org |
| `level_section` | Between semesters only |
| `grade_year` | Between semesters only |
| `section_id` | Between semesters only |
| `strand_id` | Between semesters only |
| `course_id` | Between semesters only |
| `status` | See status transition rules in DEV-02 Section 4.4 |

### 2.3 On Profile Save — Re-Enrollment Trigger

When any of `level_section`, `grade_year`, `section_id`, `strand_id`, or `course_id` changes:

```
1. Find all current active enrollments for this student.
2. For each enrollment:
     IF the class no longer matches the student's new profile:
       Soft-delete the enrollment (deleted_at = now()).
       Notify the educator: "Student [Name] has been removed from your
         class [Title] due to a profile update."
       Log in Admin Audit Log.
3. Run the full enrollment validation sequence (Section 3 below) for the
   new profile — enroll student in all newly matching classes.
```

## 3. Enrollment Validation Sequence

This sequence runs whenever a student profile is saved (create or update) and the student's status is ACTIVE.

Run checks in this exact order:

### Check 1 — Section Capacity

```
IF student.section_id is set:
  section = getSection(student.section_id)
  IF section.capacity is NULL:
    PASS  -- unlimited
  ELSE:
    count = countActiveStudentsInSection(section.id)
           -- excludes this student if they're already assigned
    IF count >= section.capacity:
      PROMPT Admin (see DEV-01 Section 6.4):
        (A) Create new section → Admin names it → assign student there.
        (B) Leave without section → student.section_id = null,
            student.status = PENDING. STOP here.
      Log to Admin Audit Log.
```

### Check 2 — Class Matching & Enrollment

```
For each class in org where:
  class.level_section = student.level_section
  AND class.grade_year = student.grade_year
  AND (class.strand_id = student.strand_id OR class.strand_id IS NULL)
  AND (class.course_id = student.course_id OR class.course_id IS NULL)
  AND (class.section_id = student.section_id
       OR class.section_id IS NULL)
  AND class.school_year_id = currentSchoolYear.id
  AND class.is_archived = false

  -- Check for existing enrollment
  existing = getEnrollment(student.id, class.id)
  IF existing (not soft-deleted):
    SKIP — already enrolled (Check 3: duplicate prevention)
    Log: "Duplicate enrollment skipped"
    CONTINUE to next class

  -- Check class capacity
  IF class.capacity IS NOT NULL:
    enrolled_count = countActiveEnrollmentsInClass(class.id)
    IF enrolled_count >= class.capacity:
      PROMPT Admin:
        (A) Create a parallel session (new class, same subject/settings,
            different weekday) → create new class → enroll student there.
        (B) Mark as Pending Enrollment for this subject.
            Store: PendingEnrollment { student_id, class_id, reason: "CAPACITY_FULL" }
      Log to Admin Audit Log.
      CONTINUE to next class

  -- Enroll
  CREATE Enrollment { student_id, class_id, enrolled_at: now() }
  Notify educator: "New student [Name] has been added to your class [Title]."
  Log to Admin Audit Log: action = "AUTO_ENROLLED"
```

### Check 3 — Duplicate Prevention

Handled inline in Check 2. If an active enrollment for the same `student_id` + `class_id` already exists, skip silently. Do not create a duplicate.

## 4. Adding an Additional Subject (Admin Only)

Use this when a student needs a class that does **not** match their standard profile — e.g. elective, retake, cross-program subject.

Educators cannot do this. Only Admin.

### 4.1 Flow

```
Step 1  Admin opens student detail view.
Step 2  Admin clicks "Add Subject".
Step 3  Admin searches for the target class by:
          class title, subject name, educator name, or semester.
Step 4  System validates:
          [ ] No existing enrollment for this student in this class (same semester)
          [ ] Class capacity not exceeded
          [ ] Student status = ACTIVE
        If any check fails, show specific error. Do not proceed.
Step 5  Admin confirms.
Step 6  Create Enrollment { student_id, class_id, enrolled_at: now(),
                            added_by: ADMIN, manual: true }
Step 7  Notify educator: "New student [Name] has been added to your class
          [Title] by Admin."
Step 8  Log in Admin Audit Log:
          action_type = "MANUAL_ENROLLMENT_ADD"
          details = { student_id, class_id, admin_id }
Step 9  If class has past assessments, educator handles status assignment
        for missed assessments (NULL / Exempted / Custom Score).
        This is an educator-side action — no further Admin step needed.
```

## 5. Removing a Subject Enrollment (Admin Only)

Educators cannot remove enrollments. Only Admin.

> Exception: Educator CAN remove a student from their class via the class roster view (e.g. wrong section placement). That action is logged in the Educator Activity Log, not Admin Audit Log.

### 5.1 Flow

```
Step 1  Admin opens student detail view.
Step 2  Admin selects an enrollment to remove.
Step 3  System checks:
          has_grades = any locked or published scores exist for this
                       student in this class?
          has_submissions = any Submitted assessments exist?
        IF has_grades OR has_submissions:
          Show warning: "This student has existing grades/submissions in
            this class. Removing them will archive their records.
            Their scores will not be wiped but will no longer appear
            in active class views. Confirm?"
Step 4  Admin confirms.
Step 5  Soft-delete the enrollment: enrollment.deleted_at = now()
        DO NOT delete scores, submissions, or attendance records.
        Those remain in the database under the soft-deleted enrollment.
Step 6  Notify educator: "Student [Name] has been removed from your class
          [Title] by Admin."
Step 7  Log in Admin Audit Log:
          action_type = "MANUAL_ENROLLMENT_REMOVE"
          details = { student_id, class_id, admin_id, had_grades: bool }
```

## 6. Pending Enrollment Resolution

When enrollment conflicts leave a student with `PENDING` status or unresolved `PendingEnrollment` records, Admin must resolve them.

### 6.1 PendingEnrollment Model

```
PendingEnrollment
  id              UUID, primary key
  student_id      FK → Student
  class_id        FK → Class
  reason          enum (SECTION_CAPACITY | CLASS_CAPACITY)
  created_at      timestamp
  resolved_at     timestamp, nullable
  resolution      enum (ENROLLED | DISMISSED), nullable
```

### 6.2 Resolution Flow

Admin sees a "Pending Students" list on the dashboard. For each:

```
Option A — Enroll now
  → Admin increases class capacity, or Admin creates a new parallel class.
  → Run enrollment for the pending student.
  → Set PendingEnrollment.resolution = ENROLLED, resolved_at = now().

Option B — Dismiss
  → Admin confirms the student will not be enrolled in this subject.
  → Set PendingEnrollment.resolution = DISMISSED, resolved_at = now().
  → If student has no other pending items and has a section assigned,
    student.status can be set back to ACTIVE.
```

## 7. Transcript

### 7.1 What It Contains

The transcript is a complete, read-only grade history for a student across all semesters and school years.

```
TranscriptView (computed, not a stored table):
  student_id
  For each school_year:
    For each semester:
      For each class the student was enrolled in:
        class_title
        subject_name
        educator_name (at time of grade finalization)
        rubric category scores
        final_grade_value
        final_grade_remark (Passed / Failed / INC / etc.)
        semester
        school_year
```

### 7.2 Rules

- Transcript is read-only. No editing by any role.
- Includes grades from archived classes and past school years.
- Includes grades from classes where the student's enrollment was later removed — those archived records are still part of the history.
- Visible to:
  - The student themselves (their own transcript only)
  - Admin
  - The educator of each class (only their own class's row)

### 7.3 Implementation Note

Do not build a separate `Transcript` table. Compute the transcript view by querying:
- `Enrollment` (including soft-deleted, where grade was locked)
- `GradeLock` records
- `ClassGrade` / rubric category scores

Filter by `student_id`. Join through `Class → SchoolYear → Semester`.
