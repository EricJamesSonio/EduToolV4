
---

**Phase 1 — Database & Schema**

Start here because literally everything else depends on it. Define your Prisma schema first — all models, relations, enums. Run your first migration. Seed a test Admin and a test Student.

Why first? Because until you have real tables, you're writing service code that calls methods that don't exist yet. You'll constantly be guessing field names.

---

**Phase 2 — Core Infrastructure (your "helpers")**

Your instinct here is right. Build in this exact sub-order:

1. `configs/` first — because logger, database, and everything else needs env vars resolved before they can initialize.
2. `core/database/` (DatabaseModule + DatabaseService) — the Prisma singleton. Everything queries through this.
3. `core/logger/` (Winston setup) — once you have this, all your future code can log properly during development instead of using raw console.log.
4. `core/middleware/request-id.middleware.ts` — short file, wire it in `main.ts` early so every log from this point forward has a request ID.
5. `core/events/` — EventEmitter2 setup. Wire it into `AppModule`. You won't use it heavily yet but it needs to exist before modules start emitting.

---

**Phase 3 — Commons (guards, pipes, filters, interceptors, decorators, utils)**

Build these before any module because modules depend on them for literally every route.

Order within Phase 3:

1. `utils/` first — `hash.util.ts`, `token.util.ts`, `date.util.ts`. Pure functions, zero dependencies, you'll need them inside AuthService.
2. `pipes/` — ValidationPipe config, ParseIntPipe. Wire the global ValidationPipe in `main.ts` now.
3. `filters/` — HttpExceptionFilter + AllExceptionFilter. Wire them globally in `main.ts`. From this point forward errors have a clean shape.
4. `interceptors/` — LoggingInterceptor + ResponseInterceptor. Wire globally. Now every response is wrapped and every request is timed.
5. `decorators/` — `@CurrentUser()` and `@Roles()`. These are tiny files but AuthGuard and RolesGuard depend on them conceptually.
6. `guards/` — AuthGuard last in this phase, because it depends on JwtService, and JwtService comes from AuthModule. You can write the guard file now but you'll fully wire it once AuthModule exists.

---

**Phase 4 — Auth Module (first and only module in isolation)**

This is the one module you build before all others because every other module needs a logged-in user to function. Until auth works, you can't test anything else.

Build it in this sub-order: entity shapes → DTOs → Repository → Service → Controller → wire AuthGuard now.

Test it end-to-end before moving on. Login should work, JWT should come back, refresh should work, the guard should block unauthenticated requests.

---

**Phase 5 — Feature Modules (in dependency order)**

Now you build the actual domain modules. The trick here is: build modules that other modules depend on first.

A good order for EduTool specifically:

1. Organization module — every other module lives inside an org.
2. School Year + Semester modules — most academic data is scoped to a school year.
3. Section module — students need sections, classes need sections.
4. Educator module — classes need educators.
5. Student module — enrollment needs students.
6. Subject module — classes are instances of subjects.
7. Class module — the central hub; lessons, assessments, attendance, grades all hang off a class.
8. Enrollment module — links students to classes.
9. Lesson module — depends on class.
10. Assessment module — depends on lesson (concept build).
11. Attendance module — depends on class and assessment.
12. Grade + GradingScale modules — depends on assessment scores.
13. Calendar module — feeds into attendance and meetings.
14. Meeting module — depends on class.
15. Notification module — depends on EventBus, wires to all above modules' events.
16. AuditLog module — same pattern as notification.
17. Export module — depends on grade and class data being finalized.
18. Analytics module — read-only aggregations, build last.
